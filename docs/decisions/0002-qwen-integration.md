# 0002. Qwen Code integration: ACP (`qwen --acp`) from the Rust core, no sidecar

Status: accepted (maintainer ratified route A on 2026-11-27). Date: 2026-11-27.

## Context

Qwen Code replaces Codex as Hearth's second agent (`docs/spec.md` §4.3). Hearth must drive the user's installed `qwen` for streaming text, tool approvals, cancel, model switch and session resume, with no network requests from Hearth's own processes and no reads of the agent's credential or config files (§6). Two routes exist in the installed package, and both are first-party:

- **A. Agent Client Protocol.** `qwen --acp` speaks JSON-RPC 2.0 over stdio, ACP protocol version 1.
- **B. stream-json.** `qwen --input-format stream-json --output-format stream-json --include-partial-messages` speaks the same envelope as the Claude Code stream-json client in ADR 0001 (`system` init, `stream_event`, `assistant`, `user`, `result`, `control_request`, `control_response`).

The spike used `qwen` 0.28.0 (the standalone install: a bundled Node 22 and `lib/chunks/*.js`, 314 MB on disk), a throwaway git repo, and a Rust harness (`serde_json` only, no async runtime) that spawns the child and parses stdout lines. The default model of this install is `qwen4-max`; every turn used the cheapest listed model `qwen3.8-flash`, except one resumed turn that was switched to `qwen3.7-plus` for the model-switch check. 9 real turns were used, of a maximum of 10: route A 4 (allowed approval, denied approval, cancel, resume with model switch) and route B 5 (simple, allowed approval, denied approval, interrupt, resume). Every spawn used `--approval-mode default` (never `yolo`, `auto` or `auto-edit`), the maintainer's existing login unchanged, and the privacy switches listed under "Privacy audit". Four extra process starts ran without a model turn: `initialize` plus `session/new` per route (to read the capabilities and model list; route A twice), and `session/resume` (no prompt).

Evidence locations below are `chunks/<file>.js:<line>:<column>` inside the installed package (`lib/` of the install dir). The code is minified into very long lines, so the column matters.

## Protocol shape

**Route A (ACP, version 1).** Agent methods (`chunk-7JDZEB77.js:3:167`): `initialize`, `authenticate`, `session/new`, `session/load`, `session/resume`, `session/fork`, `session/list`, `session/prompt`, `session/cancel`, `session/set_mode`, `session/set_model`, `session/set_config_option`. Client methods Hearth would implement (`chunk-7JDZEB77.js:3:573`): `session/request_permission`, `session/update`, plus optional `fs/*` and `terminal/*` (the spike declared none of these capabilities; Qwen reads and writes files itself). The `initialize` result reports `loadSession: true`, `sessionCapabilities: {list, resume}`, `promptCapabilities: {image, audio, embeddedContext}`, `mcpCapabilities: {http, sse}` (`acpAgent-6E2OW2VS.js:79:37418`). `session/new` returns `sessionId`, `modes` (`plan`, `default`, `auto-edit`, `auto`, `yolo`), `models` (`availableModels`, `currentModelId`) and `configOptions`. Streaming arrives as `session/update` notifications with `sessionUpdate` = `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `available_commands_update`, `usage_update`, plus Qwen's own `qwen/notify/session/*` notifications (`model-update`, `last-user-prompt`). Approvals are `session/request_permission` requests from the agent with `options[]` (`kind` `allow_once`, `allow_always`, `reject_once`) and a `toolCall` that already carries the diff (`content[].{type:"diff", path, oldText, newText}`, `locations`, `rawInput`).

**Route B (stream-json).** The control protocol is the Claude one (`session-M3KRNGMT.js:3:13090` and `3:40853`): host-to-agent `control_request` subtypes `initialize`, `interrupt`, `set_model`, `set_permission_mode`, `set_effort`, `get_available_models`, `get_context_usage`, `supported_commands`, `mcp_server_status`; agent-to-host `can_use_tool` (`chunk-TWNVRA3U.js:4:6975`, shape `{subtype:"can_use_tool", tool_name, tool_use_id, input, permission_suggestions, blocked_path}`). Approvals are delivered on stdout as `control_request` lines **only when `--input-format stream-json` is used**: with text input the headless path denies anything that needs approval without asking (`session-M3KRNGMT.js:3:32072`). The host's reply is a `control_response` `{behavior:"allow"|"deny", updatedInput?, message?}`. The `can_use_tool` request times out after 60 s by default (`DEFAULT_CAN_USE_TOOL_TIMEOUT_MS`, `session-M3KRNGMT.js:3:24662`), and a timeout is treated as a cancel; the `initialize` request accepts `timeout.canUseTool` up to 600,000 ms (`session-M3KRNGMT.js:3:15682`). That is source evidence, not a runtime test. Differences from Claude's stream: the session id comes back in the `initialize` control response before any `system` `init` line; there is an extra `stream_event` `goal_state`; `thinking_delta` and `text_delta` are separate delta types; `permission_suggestions` are `{type:"allow"|"deny", label, description}` and carry no diff.

## Options

**A. ACP client in Rust.** Spawn `qwen --acp --approval-mode default --model <m>`, send `initialize`, `session/new` (or `session/load` / `session/resume`), `session/prompt`; answer `session/request_permission`; send `session/cancel`.

**B. stream-json client in Rust.** Spawn `qwen --input-format stream-json --output-format stream-json --include-partial-messages --approval-mode default --model <m>` (add `--resume <id>`), send the `initialize` control request and user messages on stdin, answer `can_use_tool`.

## Findings that shape the client

1. **`authenticate` is destructive and must never be called.** In ACP, `authenticate` clears Qwen's cached credential file and writes `security.auth.selectedType` into the user's settings (`acpAgent-6E2OW2VS.js:79:39841`). The `initialize` result advertised one auth method (`openai`, "requires `OPENAI_API_KEY`") even though this install authenticates another way, so a generic ACP client that auto-authenticates would damage the user's setup. Hearth skips `authenticate` and learns auth state only from the first prompt's error, as the spec already says.
2. **`session/set_model` persists the choice into the user's settings unless told not to.** Without `_meta["qwen.session.modelPersistDefault"] = false` it writes `model.name`, `model.baseUrl` and `security.auth.selectedType` (`acpAgent-6E2OW2VS.js:69:141710`; flag name `chunk-DKR5CXMY.js:3:5725`). The spike always passed `false`. Hearth must too.
3. **The `session/set_model` response carries a masked API key** (`_meta.qwenModelSwitch.apiKey`, produced by `maskApiKeyForDisplay`, same location). It is masked, but it is still part of a key. Hearth must drop `_meta.qwenModelSwitch` before logging or storing a raw event; the fixtures replace the field with `REDACTED`. Route B's `set_model` response has no key.
4. **"Always allow" options write permission rules into Qwen's settings.** The request offers `allow_always` kinds (`proceed_always`, `proceed_always_project`, `proceed_always_user`). Hearth offers only `allow_once` and `reject_once` to the agent, and keeps any "always" memory in its own store. (Not exercised; read from the option names in the fixtures.)
5. **The environment question.** The `session/new` result names the environment variable that holds the provider key for each model (`_meta.envKey`). Auth worked with the environment inherited unchanged. The spike did not look at the environment, so it cannot say whether the key came from there. ADR 0001's proposal to pass only an allowlist of variables would break auth if the key is supplied as such a variable. See the question in the report.
6. **Qwen lists the user's own skills and commands to the client** (`available_commands_update`, `_meta.availableSkills`, `_meta.availableSkillDetails`, and `slash_commands` in route B's `init`; up to 660 KB per turn in route A). Hearth ignores them, and the fixtures drop everything that is not a built-in command.

## Fixtures

`fixtures/qwen/*.jsonl` are raw `qwen` stdout lines, scrubbed. Route A (chosen): `acp-initialize-new`, `acp-approval-allowed`, `acp-approval-denied`, `acp-cancel`, `acp-resume-load` (a no-tool turn after `session/load`, so it doubles as the simple turn), `acp-resume-only`. Route B, kept for the revisit conditions: `streamjson-initialize`, `streamjson-simple`, `streamjson-approval-allowed`, `streamjson-approval-denied`, `streamjson-interrupt`, `streamjson-resume`. The host's own writes are not in stdout; their shapes are in the table above and in the "Protocol shape" section.

Scrubbed by a script that is not committed: `/Users/<name>` to `$HOME`; the OS username to `USER`; any string containing a path into `~/.qwen`, `~/.claude`, `~/.codex` or `~/.ssh` to `AGENT_CONFIG_PATH_REDACTED`; `.qwen/` inside a relative doc string to `AGENT_CONFIG_DIR/`; any value of these field names to `REDACTED`: `email`, `emailAddress`, `accountUuid`, `account_uuid`, `organizationUuid`, `organization_uuid`, `organizationName`, `organization_name`, `displayName`, `userID`, `user_id`, `orgId`, `org_id`, `apiKey`, `api_key`, `accessToken`, `refreshToken`, `token` (only `apiKey` occurred, in `acp-resume-load`); `envKey` values to `ENV_KEY_NAME_REDACTED`; `availableSkills` and `availableSkillDetails` to empty lists; `slash_commands` to `["REDACTED"]`; `availableCommands` filtered to the built-in commands. Streamed text and JSON fragments that split a path across deltas were rejoined, scrubbed and re-split. Left as is: random session, call and execution ids, the provider host (`token-plan.maas.qwencloudapi.com`) and the model names with their plan label ("QwenCloud Token Plan for Global/Intl"), which identify the plan type but no account.

## Decision

**Route A: spawn `qwen --acp` directly from the Rust core and speak ACP. No Node sidecar.** (Proposed; the maintainer ratifies.)

Reasons:

- Every capability Hearth needs, (a) to (e), works on the wire in both routes, so capability does not decide.
- ACP gives a richer approval request: the diff, file locations and typed options (`allow_once`, `reject_once`) arrive in the request, where route B gives `permission_suggestions` with labels only. It has no 60 s approval timeout to configure around, and `session/load` replays history, which the transcript view can use.
- ACP is an open protocol with a published client contract, so the same client reaches other ACP agents later. Route B is Claude's envelope, but its control subtypes and timeouts are Qwen's own; it is a private SDK protocol that happens to resemble Claude's, so reusing it gains one parser, not a new agent.
- The route A hazards (findings 1 to 4) are all avoidable by client rules: never call `authenticate`, always send the persist flag, never log `_meta.qwenModelSwitch`, only offer one-shot options.

The honest cost: route B reuses most of ADR 0001's parser and has no hazards 1 to 4 (its `set_model` returns no key), so if the maintainer prefers fewer sharp edges over a generic client, B is a legitimate choice, and the fixtures for it are in place.

Revisit if any of these happen:

- A `qwen` release changes `session/request_permission`, `session/cancel`, `session/load` or `session/resume` semantics, or removes `--acp`.
- Any of finding 1 to 3 turns up on a path the client rules cannot cover (for example a method that writes settings without a flag to prevent it).
- The ACP client costs more than M1 estimates (more than a small module plus fixtures), or no second ACP agent is wanted within two milestones and route B's shared parser would save real work.
- Qwen enables usage statistics or telemetry on a path the environment variables above do not reach.

## Consequences

- M1 builds `AgentAdapter` for Qwen as a Rust ACP client: process supervision, JSON-RPC framing, `initialize` / `session/new` / `session/load` / `session/resume` / `session/prompt` / `session/cancel` / `session/set_model`, and a mapping of `session/update` to `AgentEvent` (`agent_message_chunk` to `text.delta`, `agent_thought_chunk` to `reasoning.delta`, `tool_call` and `tool_call_update` to `tool.start`, `tool.output`, `tool.end` and `file.edit`, `session/request_permission` to `approval.request`, `usage_update` to `usage`). Empty message chunks are dropped. The `AgentEvent` union in the spec needs no change.
- The Codex app-server adapter lines in `docs/spec.md` §4.3 and the detection text in §4.3 (`codex` on `PATH`) are replaced by `qwen` detection: `qwen --version`, then spawn `qwen --acp` and read `agentInfo.version` from `initialize`. The orchestrator makes that spec change separately.
- Spawn contract: the four environment variables above, `--approval-mode default` (Hearth maps its own permission modes to ACP `session/set_mode` and never launches with `yolo`), `--model` from the model list `session/new` returns (`listModels()` comes from the agent), and the client rules in findings 1 to 4. The client never declares `fs` or `terminal` capabilities, so Qwen does its own file and shell work under its own approvals.
- Approvals map to ACP option kinds. A multi-session UI must allow concurrent `session/request_permission` requests (the request id is the key) and answer `{outcome:{outcome:"cancelled"}}` when a prompt is cancelled while a request is open.
- Adopting an ACP client gives Hearth a generic route to other ACP agents (any agent that speaks `initialize` / `session/new` / `session/prompt`), but each agent still needs its own detection, auth hint and quirk rules (as the findings above show for Qwen). It does not make the adapter interface generic by itself.
- Decided by the maintainer on 2026-11-27: `web_search` and `web_fetch` stay on (their traffic is Qwen's, and each use still needs approval). "Always allow" is Hearth-side only: Hearth answers each `session/request_permission` with a one-shot option and keeps any "always allow for this thread" in its own store, so Qwen's settings are never written.
- Environment policy (finding 5), proposed, decided in M2: the maintainer brings their own provider key with a global endpoint rather than signing in to a Qwen account. Pass a fixed allowlist plus the variables each agent names itself (Qwen's `_meta.envKey` for the key, and the matching endpoint variable), never reading values. If the key and endpoint live in Qwen's own settings file, Qwen reads them itself and no variable is needed. A denylist that drops `*_BASE_URL` would break a global endpoint set by env, so it is not used.
